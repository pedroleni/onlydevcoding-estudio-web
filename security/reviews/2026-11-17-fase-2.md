## Resumen ejecutivo

La fase 2 no introduce vulnerabilidades. La defensa del salto del navegador a
las Server Actions funciona como dice la documentación: se probó contra una
build de producción con una API falsa que registraba cada escritura, y solo
el par exacto `Host: 127.0.0.1:3000` + `Origin: http://127.0.0.1:3000` llega
a escribir. Las variantes de DNS rebinding, CSRF, `Origin: null`, sin
`Origin`, `X-Forwarded-Host`, formularios `multipart` sin JavaScript, `GET` y
`HEAD` con `Next-Action` y las rutas fuera del `matcher` (`/_next/*`,
codificaciones, `..`) no ejecutan ninguna acción.

Las tres Server Actions validan en tiempo de ejecución todos sus argumentos,
reconstruyen los objetos antes de enviarlos y codifican cada segmento de la
ruta. El token no aparece en el bundle del cliente: se compiló con un valor
canario y no está en ningún archivo de `.next/`. Todo texto y URL se pinta
con JSX normal, y la URL publicada nunca se usa como `href`.

Quedan tres observaciones de endurecimiento sin ruta de explotación concreta,
que no puntúan.

## Observaciones sin puntuar

# Obs 1 (O1): Endurecimiento de la llamada a la API: `src/lib/api-escritura.ts:32-40`

- Severity: Informativo
- Description: `fetch` usa `redirect: "follow"` por defecto. Según la
  especificación Fetch, en una redirección a otro origen solo se elimina
  `Authorization`; una cabecera propia como `X-Estudio-Token` se reenvía, y
  con un 307 o 308 también el cuerpo `PUT`.
- Exploit Scenario: ninguno realista hoy. La API local no redirige a otros
  orígenes, y un proceso local capaz de ocupar `127.0.0.1:8000` también podría
  leer el `.env`. Solo importaría si `API_URL` apuntara por error a un
  servicio que redirige.
- Recommendation: añade `redirect: "error"` a la llamada de `escribir()`, y
  un test que compruebe que una respuesta 3xx no se sigue.

# Obs 2 (O2): Validación de la URL solo en el cliente y en la API: `src/lib/acciones.ts:68-80`

- Severity: Informativo
- Description: `esEstadoRed` acepta cualquier cadena en `url`. Se comprobó que
  `{"estado":"publicado","url":"javascript:alert(1)"}` pasa la Server Action y
  llega a la API. La API real lo rechaza en `EstadoRed.validar_estado`
  (`https`, lista cerrada de hosts, sin credenciales ni puerto), y la web solo
  pinta la URL como texto (`EstadoPublicacion.tsx:123-125`), así que no hay XSS.
- Exploit Scenario: ninguno con el código actual. Si una fase futura convierte
  la URL en un enlace (`<a href>`) y alguien escribe `publicacion.json` a mano
  o la API relaja su validación, la web no tendría una segunda barrera.
- Recommendation: en `esEstadoRed`, exige además
  `estado.url === null || errorUrlPublicacion(estado.url) === null`, que ya es
  código compartido y sin dependencias de navegador. Si algún día la URL se
  usa como `href`, vuelve a validarla al pintarla.

# Obs 3 (O3): El Proxy es la única defensa web de las Server Actions: `src/proxy.ts:17-26` y `src/proxy.ts:53-55`

- Severity: Informativo
- Description: la referencia de `proxy.ts` de Next 16 avisa de que cambiar el
  `matcher` o mover una Server Function a otra ruta puede quitarle la
  cobertura del Proxy sin que nadie lo note. Hoy el `matcher` solo excluye
  `/_next` y `/_next/*`, ninguna acción se atiende ahí (verificado) y
  `src/proxy.test.ts:94` fija su valor.
- Exploit Scenario: ninguno con el código actual. Un cambio futuro del
  `matcher` que excluya, por ejemplo, las rutas con punto dejaría solo la
  comprobación propia de Next (`Origin` igual a `Host`), que no detiene el DNS
  rebinding: con rebinding ambos valen `atacante:3000`.
- Recommendation: mantén el test del `matcher` y añade uno que recorra las
  rutas de `src/app` con acciones. Opcionalmente, añade en `ejecutar()` una
  comprobación barata con `headers()` de `host` y `origin`, para que cada
  Server Action se proteja también sin el Proxy.

## Verificado sin hallazgos

- **Escáneres**: `scan_code_patterns.sh`, `scan_configs.sh`,
  `scan_dependencies.sh`, `scan_prompt_injection.sh` y `scan_secrets.sh`
  terminan con 0 hallazgos. `test_scan_configs.sh` y
  `test_scanners_cobertura.sh` pasan. Los tests de `proxy`, `acciones`,
  `url-publicacion` y `medios` pasan (55 de 55).
- **Proxy y Server Actions** (build de producción con `next start`, contra
  una API falsa en otro puerto; ningún dato real):
  - `Host` y `Origin` canónicos: la acción se ejecuta (control positivo).
  - Sin `Origin`, `Origin: null` y `Origin` ajeno: 403 sin escritura.
  - DNS rebinding (`Host` y `Origin` del atacante): 403 sin escritura.
    `Host` ajeno con `Origin` canónico: 400.
  - `X-Forwarded-Host` del atacante: 403. Proxy y Next no se pueden
    desincronizar con esa cabecera.
  - `Host: localhost:3000`: solo devuelve la página de salto, sin ejecutar la
    acción.
  - Formulario `multipart` con `$ACTION_ID_` desde otro origen: 403. `PUT`
    sin `Origin`: 403. `GET` y `HEAD` con `Next-Action`: no ejecutan nada.
  - Rutas fuera del Proxy o normalizadas (`/_next`, `/_next/x`,
    `/_next/image`, `/_next/data/x`, `/%5Fnext/x`, `/_next%2Fx`,
    `/_next/../`, `/_next/%2e%2e/`, `.rsc`, `?_rsc`, `/_not-found`,
    `/index`, rutas inexistentes): ninguna ejecuta la acción. Las que no
    excluye el `matcher` reciben 403 del Proxy y las de `/_next` devuelven
    404 sin pasar por el manejador.
- **Validación de las Server Actions**: `numero` como cadena o `1e400`,
  traversal en `curso`, `pieza` y `red`, `red: "__proto__"`, `ruta` como
  objeto y `titulos` como cadena se rechazan con un mensaje fijo antes de
  llamar a la API. Los campos extra del estado se descartan al reconstruir el
  objeto. Las rutas usan `encodeURIComponent` y listas cerradas. El cuerpo se
  limita a 256 KB. Las regex son lineales.
- **Detalle 422**: solo se muestra si es una cadena, y como texto JSX. Los
  422 de la API son literales fijos sin rutas ni contenido del usuario. Los
  errores de validación de FastAPI llegan como lista y se sustituyen por un
  mensaje genérico. El `console.error` registra solo el tipo de error.
- **Token**: `api-escritura.ts` importa `server-only` y solo lo importa
  `acciones.ts` (`"use server"`). Una build `next build --webpack` con
  `ESTUDIO_TOKEN` canario no contiene el valor en ningún archivo de `.next/`.
  `.next/static` no contiene `ESTUDIO_TOKEN`, `X-Estudio-Token`, `API_URL`,
  rutas absolutas ni los mensajes de servidor de `acciones.ts`. El cliente
  solo recibe los tres identificadores de acción. La build Turbopack de uso
  diario tampoco contiene esos nombres en `.next/static`. El token solo viaja
  en los `PUT`: las lecturas `GET` no lo llevan. `.env*` está ignorado y
  `.env.example` deja el token vacío.
- **Renderizado**: no hay `dangerouslySetInnerHTML` ni `innerHTML`. Títulos,
  textos, notas, avisos, errores y la URL publicada se pintan como texto JSX.
  Los únicos `href` nuevos son consultas relativas con `encodeURIComponent`.
  `src` usa `urlMedio()`, con base `NEXT_PUBLIC_API_URL` y la ruta codificada.
  La API contiene la ruta dentro de `publicar` y solo acepta portadas
  candidatas. La validación cliente de URL (`url-publicacion.ts`) exige
  `https:`, un host de la lista cerrada y que no haya credenciales, puerto,
  espacios ni caracteres de control. Coincide con la de la API.
- **`medios.ts`**: sacar `urlMedio` de `api.ts` evita que los componentes
  cliente arrastren `API_URL`. Solo usa `NEXT_PUBLIC_API_URL`, pública por
  diseño.
- **Cadena de suministro**: la única dependencia nueva es `server-only@0.0.1`
  (MIT), descargada de `registry.npmjs.org` con `integrity` y sin scripts de
  instalación. `^0.0.1` solo admite `0.0.1`. El lockfile está sincronizado.
- **Infraestructura**: no hay cambios en `.github/`.
- **Entorno de agentes y prompt injection**: en `.claude/` solo cambia el
  texto de `security-local-api.md`. No hay permisos, hooks ni caracteres
  ocultos. Los cambios de `AGENTS.md`, `README.md` y de los precedentes
  describen lo que hace el código.
- **Historial**: ningún commit de la rama contiene rutas absolutas, emails,
  tokens ni textos reales de lecciones en el contenido. Los datos de prueba
  son ficticios.
